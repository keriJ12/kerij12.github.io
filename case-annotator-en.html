Sample Annotator — frame the photo, stamp the date and carrier, paste it into the email

A single-file web tool for the sample and sales staff of an Austrian textile company: drop a photo in, draw a box, pick a preset label, copy to Outlook. No server, no installation; the photo never leaves the user's browser. It was my first tool built by describing requirements to AI rather than writing code — about thirty requests over two days. The tool UI is in German (and Traditional Chinese).

01Context

The setting

Fabric samples arrive every day, and every photo needs the same three facts

The sample department receives a parcel, photographs it, and has to tell the customer or supplier: when it arrived, which carrier delivered it, which item and colour it is. The old way was to drop the photo into a drawing tool or Word, add text by hand, resize, save, send. Not hard, but repeated daily, and everyone's labels looked different.

Starting point

I do not write code, but I knew exactly what this should look like

Instead of opening an editor, I wrote the flow — drop a photo, draw a box, tap the date, copy to email — as requirements, had AI build it, then tested with real photos and reported what was wrong. Around thirty requests in two days, from “the box must be draggable” to “pasting into Outlook must not blow up the message”. The process later became a tutorial for non-programmers.

02Problem

Problem statement

The tool should save the time spent deciding, not the time spent drawing

Font size, colour, date format, how large a file still sends — every one of these was decided again each time. So the goal was not a full-featured image editor, but to turn the department's few recurring decisions into defaults, leaving the user with only two: where to frame, and what to write.

Scope

Built — and deliberately not built

Built

  • Open a photo by button, drag-and-drop or Ctrl+V
  • Box, circle and text-only annotations, drawn by dragging
  • Preset chips: item, colour, variant, date (today's date filled in)
  • Rotate, non-destructive crop, undo/redo
  • Download (choice of size) and “copy to email” (its own size)
  • Preferences remembered in the browser; dark mode follows the system

Deliberately not built

  • Uploading anywhere, accounts, share links
  • Multi-select, grouping, rotated labels, multi-line text
  • Saving annotations as a project to reopen later
  • Filters or retouching

03Design decisions

Decision · First screen

A sample photo is already there, so nobody has to find a file first

First-time users get stuck on “where do I find a photo?”. The Chinese version opens with a generated sample photo and two sample labels; one drag and the interaction is understood. Because the image is drawn by code, the file contains no real fabric sample. The German version for colleagues deliberately keeps an empty drop zone.

Decision · Presets

Date and carrier are the default labels, and presets insert rather than replace

What matters on the day a sample arrives is “which date, which carrier”, so the sample labels and placeholders use a “date – carrier” format with today's date computed by the tool. Preset chips insert text at the cursor instead of overwriting, because real labels are combinations like “Item 123 Colour 05”.

Decision · Output

“Copy to email” is a separate button with its own size

A photo in an email does not need the original resolution; a long edge of 1280 px is readable without bloating the message. Download keeps the original size for archiving. Two buttons, two remembered sizes, no switching settings between the two uses.

Decision · Reversible

Crop is non-destructive; every completed action is one undo step

Cropping only records a region; the original image and annotation coordinates stay put, so it can be reverted, undone, and it rotates with the image. Finishing a box, a drag, or closing the edit card each counts as one step; changing colours while the card is open does not flood the history.

Decision · No fighting the tool

Only the outline of a shape is selectable; font size scales with the photo

Clicking inside a large box draws a new box rather than selecting the old one — to select, click its edge. Font size is a per-mille of the photo's long edge, so the same setting looks proportional on a 1500 px and a 4000 px image, and labels scale with the output.

04Approach & tech

How it was built

One requirement at a time, accepted with real photos

  • Flow first, features second. The first request described the whole usage flow, not “a box-drawing tool”.
  • One change per round, tested on real photos immediately. Boxes that would not drag, text too small, Outlook paste too large — all found by trying.
  • Say why. “Email photos do not need full size” is the sentence that produced the separate email size setting.
  • The German version is the same program with different strings and font, so behaviour cannot drift apart.
Technical notes

One canvas, a few browser APIs, no framework

  • Canvas 2D: photo, boxes, circles, label backgrounds, outlines, selection dashes and crop mask all on one canvas; export uses an offscreen canvas to apply crop and scale in one pass.
  • Clipboard API: the result is written to the system clipboard as PNG; unsupported browsers fall back to a preview the user can right-click.
  • Pointer Events: one code path for mouse and touch.
  • localStorage: colours, font size, backgrounds, output and email sizes, all wrapped in try/catch so private windows still work.
  • Single HTML of about 60 KB; Google Fonts is the only external resource.

05Limits & lessons

Limits

A handy small tool, not an image editor

“Copy to email” depends on the browser being able to write images to the clipboard; some mobile browsers fall back to manual copying. Annotations cannot be saved as a project — close the page and only the downloaded image remains. One label selected at a time, single-line centred text. A never-called “recent labels” function remains in the code as a leftover of development; the portfolio version does not wire it up.

Lesson

Describing a requirement well enough to be built is itself design work

This tool confirmed something: I do not need to write every line, but I must be able to say where the user is, what they have in hand, and what decision comes next. The WEAVE workspace and the care-label composer were built the same way.
